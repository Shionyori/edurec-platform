# 教育资源推荐系统 · 完善方案

> 目标：把 `edurec-platform`（服务侧/数据治理侧）+ `edurec-engine`（算法侧）建设为一个
> **完整、可评估、可闭环**的教育资源推荐系统。
> 定位：不是内容站，不是搜索引擎，是**推荐系统**。
> 范围：不含学习路径/掌握度/测评（属另一个选题）。

---

## 0. 实施状态（2026-11）

两仓均在 `main`；engine 的模型与契约已合并，platform 侧按 `scripts/handoff.sh` 刷新。

| 阶段 | 里程碑 | 状态 |
|---|---|---|
| P0 打通链路 | 快照导正文、engine 批量推理入口、handoff 修正、点击/收藏/曝光上报 | ✅ 已完成 |
| P1 内容结构化 | 资源难度/时长字段、导入映射、快照导出与 engine 读取 | ✅ 已完成 |
| P2 模型补全 | 多路召回 / 多目标排序 / 重排（engine） | ⏳ 未开始（研究性工作） |
| P3 评估中心 | 运行记录与可追溯、管理后台效果看板、离线评估命令 | ✅ 已完成 |
| P4 服务增强 | 结果可追溯、推荐理由透出、注册后兴趣引导（冷启动） | ✅ 已完成 |

### 已完成的关键交付

- **反馈信号**：曝光（独立 `resource_impressions` 表，不污染 behaviors 正样本）、点击（资源卡片）、收藏（详情页）。
- **链路打通**：`export_snapshot` 导出 `description`/`difficulty`/`duration_minutes`；engine 的 `scripts/run_batch_infer.py` 产出推荐结果 + 旁挂信封；`handoff.sh` 调用真实入口并在交接前跑契约校验。
- **可追溯**：`recommendation_runs` 记录每次运行的 run_id / 快照 / 模型 / 生成时间 / 导入统计；`recommendations.run_id` 关联到用户。
- **可解释**：信封 reasons 落库并在首页卡片透出。
- **可度量**：`GET /admin/recommendation-stats` 提供曝光/点击/CTR；`cmd/evaluate_recommendations` 对比「实际推荐 vs 热门基线」。
- **冷启动**：`users.interests` + 兴趣兜底 + 首页兴趣引导。

### 仍未做（P2，engine 侧）

多路召回融合（当前是语义单路 + 质量融合）、学习排序（多目标）、规则重排的显式回归。
这部分需要实验与调参，属研究性工作，本方案保留接口不变、模型可替换的契约。

## 1. 定位与目标函数

### 1.1 一句话定位

| 角色 | 仓库 | 职责 |
|---|---|---|
| 数据治理 + 在线服务 | `edurec-platform` | 多源内容入池、用户与反馈采集、推荐结果服务化、评估与运营后台 |
| 推荐算法本体 | `edurec-engine` | 特征、多路召回、多目标排序、重排、离线评估 |

### 1.2 目标函数（第一设计决策）

通用推荐系统优化**点击率/时长**。教育推荐若照抄，会退化为标题党，与 B 站无异。故：

```
学习价值 ≈ 相关性 × 难度匹配 × 完成/满意概率
```

- **相关性**：内容主题与学习者需求匹配（语义，而非关键词）
- **难度匹配**：太难劝退、太易无聊（最近发展区）
- **完成/满意概率**：点开不算数，学完/收藏/好评才算数

此决策决定：采什么信号、提什么特征、排什么序、评什么指标。

### 1.3 与相似系统的边界

| 系统 | 解决的问题 | 本系统关系 |
|---|---|---|
| B 站搜索 | "我知道要什么，帮我找到" | 不做这个 |
| B 站推荐 | 最大化观看时长 | 目标不同（学习价值 vs 消费时长） |
| 学习路径/知识图谱 | "按什么顺序学" | **另一选题，本方案不做** |

## 2. 教育场景的 5 个特殊性

| 特殊性 | 设计含义 |
|---|---|
| 目标是学习不是消费 | 多目标（点击 + 完成 + 满意），拒绝纯 CTR |
| **交互极稀疏**（每人几条） | 协同过滤不可靠 → 内容/语义/结构化特征更重要 |
| 内容有丰富内在结构 | 学科、难度、时长、格式均可作为特征 |
| 反馈类型多且语义不同 | view/click/favorite/complete/rating，权重差异大 |
| 冷启动是常态 | 新用户带目标而来 → 目标/兴趣引导 + 内容侧兜底 |

## 3. 目标架构

```
┌──────────────────────────────────────────────────────────┐
│ 服务层    多场景推荐 · 搜索 · 详情 · 反馈上报              │
│           曝光打点 · 结果版本 · 推荐解释 · 降级兜底        │
└────────┬───────────────────────────────────┬─────────────┘
         │                                   │
┌────────▼─────────┐              ┌──────────▼─────────────┐
│ 反馈/日志层       │              │ 推荐结果存储            │
│ 曝光·点击·收藏·完成│             │ (user → 有序资源列表)   │
└────────┬─────────┘              └──────────▲─────────────┘
         │                                   │
         │                        ┌──────────┴──────────┐
         │                        │ 离线批量推理          │
         │                        └──────────▲──────────┘
         │                                   │
┌────────▼───────────────────────────────────┴─────────────┐
│ 模型流水线 (engine)                                       │
│  多路召回 → 多目标精排 → 重排(难度梯度/多样性/新鲜度)      │
│  离线评估 + 基线对比                                       │
└────────┬─────────────────────────────────────────────────┘
         │
┌────────▼─────────────────────────────────────────────────┐
│ 特征层  用户画像 · 内容特征(语义/结构化/质量) · 交叉特征    │
└────────┬─────────────────────────────────────────────────┘
         │
┌────────▼─────────────────────────────────────────────────┐
│ 数据层 (platform)  多源内容(统一ID) · 用户 · 行为反馈 ·     │
│                    分类 · 快照导出(版本化契约)             │
└──────────────────────────────────────────────────────────┘
```

| 层 | 职责 | 关键设计 |
|---|---|---|
| 数据层 | 汇成可训练、可复现的数据 | 统一 ID 空间；**多类型反馈**；快照带版本 |
| 特征层 | 用户/内容 → 模型可用表示 | 内容语义 + 结构化属性；行为反推画像 |
| 召回层 | 全量 → 几百候选 | **多路并行**（语义/热门/协同），单路脆弱 |
| 排序层 | 候选精确打分 | **多目标**（点击/完成/满意），非单一 CTR |
| 重排层 | 满足约束 | 去重、多样性、难度梯度、新鲜度 |
| 服务层 | 稳定、可解释、可追溯 | 降级兜底、结果版本、推荐理由 |
| 评估层 | 证明有效 | 离线指标 + 基线 + 在线反馈 |
| 反馈层 | 闭环 | 行为 → 快照 → 训练 → 推荐 |

## 4. 现状与差距

对照 §3 逐层核对（2026-11）：

| 层 | 应该有的 | 现状 | 判断 |
|---|---|---|---|
| 数据·内容 | 多源统一 + 结构化属性 | 多源统一 ✅；正文/难度/时长已随快照导出 ✅ | 达标 |
| 数据·用户 | 画像 + 目标 | 平台有 `interests` 与初始问卷；engine 从行为反推需求 | 可用 |
| 数据·反馈 | 曝光 + 点击 + 收藏 + 完成 | 曝光/点击/收藏已上报 ✅；**完成（complete）尚未建模** | 基本可用 |
| 特征 | 用户/内容/交叉 | engine 有文本编码 + 热度/评分融合 ✅；平台不做特征 | 单薄 |
| 召回 | 多路 | engine **仅单路语义 + 质量融合** | 待补 |
| 排序 | 多目标学习排序 | **无学习排序**，仅线性质量融合 | 待补 |
| 重排 | 去重/多样性/难度/新鲜度 | 出口过滤已交互 + top-N；无多样性/难度约束 | 待补 |
| 服务 | 多场景/解释/版本 | 首页单场景；有推荐理由与 `run_id` 追溯 | 半成品 |
| 评估 | 离线 + 基线 + 在线 | engine 有离线指标与基线 ✅；platform 有运行记录/CTR/离线评估 ✅ | 达标 |
| 闭环 | 反馈回流 | 行为/曝光落库 → 快照 → 训练 → 导入 ✅ | 成立 |

**结论**：数据治理、反馈采集、服务与评估链路已打通；**模型侧的多路召回/学习排序/重排**
是下一阶段（P2）的主要工作。它属于研究性工作，不影响现有契约：platform 只认
「快照进、排名 ID 出」，换模型不需要改 platform 代码。

### 4.1 已解决的历史断点

1. ✅ `export_snapshot` 已导出 `description`（以及 `difficulty` / `duration_minutes`），
   engine 能读到非空正文。
2. ✅ 批量推理入口统一为 `scripts/run_batch_infer.py`；旧文档里的
   `scripts.train_all` / `scripts.infer_batch` 已清理。
3. ✅ `handoff.sh` 调用真实入口，并在交接前后校验快照/产物。
4. ✅ 曝光、点击、收藏上报已落地；`impression` 独立于 `behaviors`，不污染正样本。
5. ✅ 推荐运行记录（run_id / 快照 / 模型 / 生成时间 / 导入统计）与效果看板已落地。

## 5. 剩余路线（P2，engine 为主）

| # | 任务 | 验收标准 |
|---|---|---|
| 1 | 多路召回（语义 + 热门 + 协同/内容） | 各单路与融合的离线指标可对比；出口显式去重 |
| 2 | 多目标排序（pClick / pComplete / pSatisfy） | 精排 AUC 与融合指标优于单信号 |
| 3 | 重排（多样性/难度梯度/新鲜度） | 去重率 100%，多样性/新鲜度可度量 |
| 4 | 完成信号（complete）采集与建模 | `behaviors` 或独立表有完成事件，进入快照与训练 |

约束：P2 只改 engine 与快照字段（新增列必须向后兼容），**不改主文件形状**；
任何破坏性变更先升 `contract_version` 并同步两侧校验。

## 7. 明确不做（现阶段）

- ANN 索引（资源量小，全量点积更简单精确）
- 实时在线推理（batch 形态已够，数据量不足）
- 复杂深度排序模型（先多路召回 + 浅层多目标）
- 学习路径 / 知识图谱 / 掌握度 / 测评（属另一选题）

## 8. 风险与依赖

| 风险 | 缓解 |
|---|---|
| engine 仓库改动需另行提交（跨仓） | 每个 engine 任务单独提交；契约先改 `contracts/v1` 再同步 |
| engine 语义模型单独用弱于热门基线 | 已用「语义 + 热度融合」；后续以离线指标为准 |
| 曝光打点放大数据量 | 批量写入 + 定期清理，先保证有数据 |
| 结构化字段历史数据缺失 | 允许为空，逐步回填，不阻塞链路 |
| platform 数据量小 | 先积累真实行为，再评估模型收益 |

## 附：与 B 站搜索的区别（答辩口径）

> B 站搜索解决"我知道要什么、帮我找到"；本系统解决"我不知道学什么、帮我选"。
> B 站推荐只服务观看时长；本系统推荐的目标是**学习价值**，并用内容语义 + 结构化特征 +
> 学习者行为建模，在教育这种**交互稀疏**的场景比协同过滤更可行，且结果**可评估、可追溯**。
